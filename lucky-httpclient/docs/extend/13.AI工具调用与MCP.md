# 13. AI 工具调用与 MCP

`com.luckyframework.httpclient.generalapi.ai` 提供与厂商无关的「AI 会话 + 工具调用」能力：业务侧只声明一个会话接口方法并加上 `@EnableToolCall`，即可得到「发请求 → 模型要求调用工具 → 本地执行 → 结果回填 → 带历史重放 → 最终答案」的有界回环；外部 MCP server 的远端工具可以像本地方法一样被登记与调用。

分层只有一处允许出现厂商差异：

| 层 | 包 | 职责 |
|---|---|---|
| 数据模型 | `ai.chat` | `ChatRequest`/`ChatMessage`/`ContentPart`/`ChatResponse`/`Usage`，按 OpenAI chat/completions 形状表达 |
| 工具声明 | `ai.tool` | `@Tool`/`@Param` 生成 JSON Schema，`ToolRegistry` 集中登记声明 + 执行实现 |
| 厂商方言 | `ai.vendor` | `VendorAdapter` 的三家实现 + 三套内置会话接口；业务代码与回环引擎里没有 `if (vendor == ...)` |
| 回环引擎 | `ai.loop` | `@EnableToolCall` + `FunctionCallingRunner`（阻塞与流式共用同一份轮次/失败语义） |
| MCP | `ai.mcp` | JSON-RPC 2.0 + stdio / Streamable HTTP 两条传输 + 工具桥接 |

硬约束：Java 8、零新增第三方依赖、全部行为可离线验证。

## 1. 快速开始（一个能跑通的最小例子）

### 1.1 配置文件

连接信息与密钥只来自配置文件，代码里不出现任何硬编码地址：

```yaml
# src/main/resources/ai/openai/api-config.yml
ai:
  openai:
    baseUrl: "https://api.deepseek.com/"    # 换 base-url 即可复用 OpenAI 兼容簇（DeepSeek/通义/Kimi/智谱/豆包/Ollama…）
    apiKey: "sk-从环境变量或密钥中心注入"
```

### 1.2 声明工具

```java
import com.luckyframework.httpclient.generalapi.ai.tool.Param;
import com.luckyframework.httpclient.generalapi.ai.tool.Tool;

public class WeatherToolHolder {

    /** 工具名默认取方法名，desc 必填（缺失时注册阶段直接失败并指出方法） */
    @Tool(desc = "查询城市天气")
    public Map<String, Object> get_weather(@Param(desc = "城市名", required = true) String city) {
        Map<String, Object> weather = new LinkedHashMap<>();
        weather.put("temp", 12);
        weather.put("weather", "晴");
        return weather;
    }
}
```

生成的 JSON Schema 与 `tool-declaration` 契约一致：

```json
{
  "type": "object",
  "properties": {"city": {"type": "string", "description": "城市名"}},
  "required": ["city"]
}
```

### 1.3 会话接口 + 启用回环

```java
import com.luckyframework.httpclient.generalapi.ai.chat.ChatRequest;
import com.luckyframework.httpclient.generalapi.ai.chat.ChatResponse;
import com.luckyframework.httpclient.generalapi.ai.loop.EnableToolCall;
import com.luckyframework.httpclient.generalapi.ai.vendor.OpenAIChatResponseConvert;
import com.luckyframework.httpclient.proxy.annotations.*;

@ServerAddress(url = "#{ai.openai.baseUrl}")
public interface WalkingSkeletonApi {

    @Post("/chat/completions")
    @StaticHeader("Authorization: Bearer #{ai.openai.apiKey}")
    @EnableToolCall
    @ResultConvertMeta(convert = @ObjectGenerate(OpenAIChatResponseConvert.class))
    ChatResponse chat(@JsonBody ChatRequest request);
}
```

### 1.4 调用

```java
ToolRegistry.getDefault().register(new WeatherToolHolder(), true);   // 扫描 @Tool 方法，声明与执行实现成对登记

AiConfiguration configuration = AiConfiguration.load("classpath:ai/openai/api-config.yml");
HttpClientProxyObjectFactory factory = new HttpClientProxyObjectFactory();
configuration.install(factory);                                      // 把 ai.* 配置项交给SpEL根变量，注解里的 #{ai.openai.*} 由此取值
WalkingSkeletonApi api = factory.getProxyObject(WalkingSkeletonApi.class);

ChatRequest request = new ChatRequest("deepseek-chat");
request.addMessage(ChatMessage.system("你是一个助手"));
request.addMessage(ChatMessage.user("北京今天天气怎么样？"));

ChatResponse response = api.chat(request);
System.out.println(response.getContent());    // → 北京今天晴，12 度。
```

这一次调用发出 2 个 HTTP 请求：第 1 轮模型返回 `finish_reason=tool_calls`，框架执行 `get_weather` 并把结果回填，第 2 轮带着 4 条消息（原 2 条 + 1 条 `assistant.tool_calls` + 1 条 `role=tool`）重放，拿到文本后结束。`WalkingSkeletonTest` 断言的正是这条链路。

## 2. 会话模型（`ai.chat`）

- **null 字段一律省略**：未设置的 `temperature`、`max_tokens` 不会以 `null` 占位出现在请求体里。
- **未知字段一律忽略**：厂商新增字段不会打断反序列化。
- **消息内容两种写法**：`ChatMessage.user("文本")` 输出字符串 `content`；`ChatMessage.user(List<ContentPart>)` 输出分片数组（`text` 分片 + `image` 分片，图片支持 URL 与 base64 内联，模型层不出现任何厂商字段名）。
- **扩展容器**：`request.putExtra("service_tier", "standard")` / `message.putExtra(...)` 里的键值原样输出到对应 JSON 层级，用于承载厂商专属参数。
- **角色工厂方法**：`system` / `user` / `assistant` / `assistantToolCalls(List<ToolCall>)` / `toolResult(toolCallId, result)` / `toolResult(toolCallId, result, isError)`。
- **结束原因归一**：`stop`（OpenAI `stop`、Anthropic `end_turn`、Gemini `STOP`）、`length`、`tool_calls`（Anthropic `tool_use`、Gemini 存在 `functionCall` 分片时）。
- **用量归一**：`Usage` 的输入/输出/总数三项，缺失时为「未提供」而非报错。
- **`copy()`**：消息列表新建 `ArrayList`、其余字段浅复制；回环只在副本上追加消息，**业务传入的请求对象不会被就地修改**。
- 内部控制字段 `loopRound` 为 `transient` 且不参与序列化，绝不会泄漏进请求体（`ChatSessionModelTest#loopRoundNeverLeaksIntoBody`）。

## 3. 工具声明的三种来源（`ai.tool`）

三种来源进入 `ToolRegistry` 后是同一数据结构（`ToolSpec` + `ToolExecutor`）：

```java
ToolRegistry registry = new ToolRegistry();                 // 也可用 ToolRegistry.getDefault() 全局默认实例

// ① 注解生成：扫描对象里的 @Tool 方法，并把该方法绑定为执行实现
registry.register(new WeatherToolHolder());
registry.register(new WeatherToolHolder(), true);           // 同名时覆盖

// ② 编程式登记
registry.register(new ToolSpec("get_weather", "查询城市天气", ToolSpec.emptyParameters()),
        args -> "北京今天晴，12 度");                         // ToolExecutor.execute(Map) 返回可序列化对象

// ③ 仅声明（无执行实现）：工具仍可被列举并出现在报文里，被调用时返回「无执行实现」的失败结果
registry.register(new ToolSpec("get_weather", "查询城市天气", schema));

// 子集：返回快照，不修改原表；@EnableToolCall(tools=...) 用的就是它
ToolRegistry subset = registry.select("get_weather");

List<ToolSpec> specs = registry.listSpecs();                // 列举顺序稳定
Optional<ToolExecutor> executor = registry.findExecutor("get_weather");
```

- **同名冲突不静默**：第二次登记抛 `ToolRegistryException`，第一次内容保持不变；需要覆盖用带 `overwrite` 的重载。
- **参数名来源**：优先 `Parameter#getName()`（本仓编译已开 `-parameters`），`@Param(name = "...")` 可显式覆盖（`properties` 与 `required` 同步换名）；反射只能得到 `arg0` 形态时，注册抛异常并给出类名、方法名与参数位置。
- **类型映射表**：`String`→`string`；整数族与 `BigInteger`→`integer`；`double`/`float`/`BigDecimal`→`number`；布尔→`boolean`；枚举→`string` + 按常量声明顺序的 `enum`；数组与集合→`array` + 由元素类型递归决定的 `items`；`Date`/时间类型→`string`；`Optional<T>` 按 `T` 处理且不进 `required`；未覆盖类型（如 `InputStream`）在注册阶段抛异常并给出类型全名，不会产出半份 schema。
- **POJO 递归展开**：字段进 `properties`，字段描述取字段上的 `@Param`/`@ParamDesc`，必填按层归属分别进入根 `required` 与该对象 schema 的 `required`；深度上限 4，自引用/相互引用抛异常并输出引用链。生成结果按 `Method` 缓存，多轮调用不重复反射。
- **结果序列化**：字符串与基本类型取其文本；对象、集合、Map 序列化为 JSON 文本（如 `{"temp":12,"weather":"晴"}`）。
- **注意同名混淆**：`ai.tool` 的 `@Param`/`@Required` 是 AI 工具参数描述注解，与 `com.luckyframework.reflect.Param`、`lucky-validator` 的 `@Required` 无关，import 时按包名区分。

## 4. 回环行为（`ai.loop`）

```java
@EnableToolCall(
        tools = {"get_weather"},                     // 本次调用可用的工具子集，不填取注册表全集
        registry = "#{myToolRegistry}",              // SpEL取注册表bean/实例，不填用默认实例
        maxRounds = "3",                             // 轮次上限，默认5，支持SpEL（如 "#{ai.streamTest.maxRounds}"）
        failurePolicy = ToolCallFailurePolicy.CONTINUE,  // CONTINUE（默认）把失败回填给模型自纠；ABORT 首个异常即上抛
        dialect = "#{openAIDialect}"                 // 流式回环必填（用于创建增量拼接器），阻塞式可不填
)
```

- **每轮都是重新调用代理方法**：插件命中后不重复 `proceed()`，而是经 `ExecuteMeta#getProxy()` + 同一 `Method` + 新参数数组重新发起，因此 base-url、鉴权头、重试、日志脱敏、Mock、响应转换器全部自动复用；防重入靠 `ChatRequest.loopRound`（跨线程也不丢）。
- **有界终止**：达到上限仍在要求调用工具时抛异常，文本含「轮次上限 N」与最后一轮待执行的工具名和参数，且不会发出下一次请求。
- **五类失败统一回填**（默认策略下不抛给业务方）：执行异常（内容含工具名与错误摘要）、未知工具（`未知工具 <name>`）、参数文本非法 JSON、必填缺失、有声明无执行实现。校验顺序固定为「JSON 合法性 → 按 schema 取值并用 `ConversionUtils` 做单值转换 → 必填检查」，三类校验失败在调用执行器之前判定。
- **同轮多调用完整**：结果严格按响应中的调用顺序逐条回填，条数与调用条数一一对应（部分失败也两条俱全），保证 Anthropic 按 `id`、Gemini 按 `name` 的配对不断裂。
- **未标注 `@EnableToolCall` 的方法行为完全不变**：请求体不注入 `tools`，响应里出现工具调用也不执行、不重放。
- 三家 `capabilities` 中「并行工具调用」与「schema 严格模式」一律上报不支持，引擎按串行执行；未知能力标志名返回不支持而非抛异常。

## 5. 流式（`@Sse` + 工具调用）

```java
@Post("/chat/completions")
@Sse
@EnableToolCall(registry = "#{myToolRegistry}", dialect = "#{myDialect}")
void stream(@JsonBody ChatRequest request, EventListener listener);
```

```java
factory.addSpringElRootVariable("myToolRegistry", ToolRegistry.getDefault());
factory.addSpringElRootVariable("myDialect", new OpenAIDialect());   // 流式必须有方言，它负责创建增量拼接器
```

- 业务只写自己的 `EventListener`，收到的是**拼接后的文本增量**；框架的 `ToolCallStreamListener` 只截留「完整工具调用」，执行完再以同一 listener 发起下一轮流式调用，`onCompleted` 只在最后一轮触发——业务看到一个连续流。
- 拼接规则（帧序列可直接离线断言，`StreamAccumulator` 是纯数据变换）：
  - OpenAI 兼容簇：按 `choices[0].delta.tool_calls[].index` 分桶，`id` 与 `function.name` 取该 `index` 首帧，`function.arguments` 增量按到达顺序连接；`delta.content` 与工具增量互不干扰。参数文本被任意切分（甚至逐字符）结果不变。
  - Anthropic：`content_block_start` 给 `index`/`id`/`name`，`content_block_delta` 的 `input_json_delta.partial_json` 按 `index` 连接，`content_block_stop` 才算完整；文本块与工具块分桶处理。
  - Gemini：`parts[].functionCall` 单帧即完整，多帧文本与调用按到达顺序透传。
- **半成品不可见**：未收到结束信号（OpenAI 的 `finish_reason`/`[DONE]`、Anthropic 的 `content_block_stop`）前不对外暴露工具调用。
- **异常终止有确定行为**：流未给结束信号即断开、或结束时参数文本仍不是合法 JSON，抛协议异常并给出工具名与已拼接的参数前缀，绝不返回可能被截断的调用。
- 流式的轮次上限与失败回填与阻塞式共用同一份 runner 语义。

## 6. 厂商方言 = 选接口（`ai.vendor`）

不存在「配置 vendor 枚举 + 框架内 switch」：URL、鉴权头、报文形状本来就是注解 API 的表达内容，换接口即换厂商。

| 内置接口 | 目标地址 | 鉴权/协议头 | 配置键 |
|---|---|---|---|
| `OpenAIChatApi` | `@Post("/chat/completions")` | `Authorization: Bearer #{ai.openai.apiKey}` | `ai.openai.baseUrl` / `ai.openai.apiKey` |
| `AnthropicChatApi` | `@Post("/v1/messages")` | `anthropic-version: 2023-06-01` + `x-api-key: #{ai.anthropic.apiKey}` | `ai.anthropic.baseUrl` / `ai.anthropic.apiKey` |
| `GeminiChatApi` | `@Post("/models/{model}:generateContent")`（`@Path("model")` 取模型名） | `x-goog-api-key: #{ai.gemini.apiKey}` | `ai.gemini.baseUrl` / `ai.gemini.apiKey` |

三家的入参与返回都是 `ChatRequest` / `ChatResponse`，差异全部留在方言里：

| 差异点 | OpenAI 兼容簇 | Anthropic | Gemini |
|---|---|---|---|
| 工具声明 | `tools[].function.parameters` | `tools[].input_schema` | `tools[0].functionDeclarations[].parameters`（类型名大写 `OBJECT`/`STRING`…） |
| system | `messages[].role=system` | 顶层 `system` 字符串（多条按先后换行连接） | 顶层 `systemInstruction.parts[].text` |
| 助手角色 | `assistant` | `assistant` | `model` |
| 工具调用 | `assistant.tool_calls[]` | `assistant.content[].tool_use` | `model.content[].functionCall` |
| 工具结果 | `role=tool` + `tool_call_id` | `user.content[].tool_result` + `is_error` | `user.content[].functionResponse`（按 `name` 配对） |
| 调用标识 | 报文自带 | 报文自带 | 报文无 → 解析时合成同一次响应内唯一稳定的标识 |
| 必填项 | — | 必带 `max_tokens`：业务未填时取方言默认值（默认 `1024`；`new AnthropicDialect(null)` 表示未配置，此时**在发出 HTTP 请求之前**抛指明缺失字段的异常） | 按模型标识与 `generateContent`/`streamGenerateContent` 决定地址 |

业务自建接口时，把方言交给 `@JsonBody(serialization = @ObjectGenerate(XxxBodySerialization.class))` 与 `@ResultConvertMeta(convert = @ObjectGenerate(XxxChatResponseConvert.class))` 即可复用同一套翻译；自定义 Anthropic 缺省 `max_tokens` 用 `new AnthropicBodySerialization(new AnthropicDialect(2048))`。

## 7. MCP（`ai.mcp`）

远端工具与本地注解工具在注册表、报文工具列表与回环行为上不可区分。

### 7.1 配置形态（`ai.mcp.<serverName>`）

```yaml
ai:
  mcp:
    weather:                        # stdio：拉起子进程，标准输入输出交换换行分隔的JSON帧
      command: java
      args: ["-cp", "target/test-classes", "com.x.FakeMcpServer"]
      env: { MCP_TOKEN: "从密钥库注入" }
      timeoutMillis: 5000
    remote:                         # Streamable HTTP：地址与请求头
      url: "http://127.0.0.1:18080/mcp"
      headers: { Authorization: "Bearer 从密钥库注入" }
      timeoutMillis: 2000
```

也可以编程式配置：`McpServerConfig.builder("remote").url(url).headers(headers).timeoutMillis(2000).build()`。`toString()` 不含请求头与环境变量的值，凭据不会因打印配置对象进日志。

### 7.2 握手、拉清单、登记

```java
McpServerConfig config = McpServerConfig.from(AiConfiguration.load("classpath:ai/mcp/mcp-config.yml"), "weather");
try (McpClient client = new McpClient(config.createTransport(), config)) {
    client.initialize();                                        // initialize 请求 → 响应 → notifications/initialized（无id）
    List<ToolSpec> registered = new McpToolBridge(client).registerAll(ToolRegistry.getDefault());
    boolean alive = client.ping();                              // result:{} 即成功，无响应则超时失败
}
```

- 未握手就请求工具清单会抛「会话未初始化」且不发请求；server 返回的协议版本与请求不一致时采用 server 版本；`capabilities` 不含 `tools` 时不注册任何远端工具并给出可诊断说明。
- `tools/list` 带 `nextCursor` 时自动续拉直至取完；`inputSchema` 原样保留为参数 schema，缺失时补 `{"type":"object","properties":{}}`。
- 重名默认抛冲突异常；需要共存时用 `new McpToolBridge(client).prefix("weather")`（注册名带前缀，远端 `tools/call` 仍用原始名）。
- `tools/call` 结果转换：`content[]` 的 text 分片按序换行连接；`isError=true` 与 JSON-RPC `error` 都转成失败结果交给回环回填（不抛给业务方）；非 text 分片不静默丢弃，输出 `[非文本分片 type=..., mimeType=...]` 占位说明。
- 通知（含 `notifications/tools/list_changed`）只容忍不报错、不打断 `id` 配对；本版本不自动刷新注册表，需要刷新请业务显式重新 `tools/list`。
- Streamable HTTP 传输自带：`Content-Type: application/json` + `Accept: application/json, text/event-stream`；响应为单 JSON 直接取、为 SSE 时按帧取与请求 `id` 匹配的消息；`Mcp-Session-Id` 由客户端持有并在后续请求头注入；收到 404 重握手一次并重发，再失败即报错（不无限重试）。stdio 传输超时或子进程退出时回收进程（`destroyForcibly`），`close()` 幂等。
- 凭据保护：MCP HTTP 头与厂商 `Authorization` 都走框架既有的按名脱敏链路（`@Masker`），开启调试日志时被脱敏键的令牌值不出现明文，其余请求信息仍可读。

## 8. 离线自测方式

全部能力可在无公网、无真实 API key 的环境下断言，`mvn -o -pl lucky-httpclient test` 即回归入口（ai 包 30 个测试类）：

| 场景 | 手段 |
|---|---|
| 报文形状 | golden-file：`src/test/resources/ai/{openai,anthropic,gemini}/*.json` 与方言输出逐字段比对 |
| 回环轮次与回填 | `@Mock` 的 `方法名$Mock` 静态方法（可注入 `Request`）按当前请求体消息数选样本，断言「发了几轮、第二轮多了哪两条消息」 |
| 「是否真发请求 / 请求次数」 | `TestHttpServer`（路径命中计数、SSE 截断与挂起场景），Anthropic 缺省 `max_tokens` 的用例断言命中数为 0 |
| 流式拼接 | 直接以帧列表喂给 `StreamAccumulator`；端到端用 `SseMock.resource(...)` 回放录制的 SSE 文本 |
| MCP stdio | 测试自带的 `support/FakeMcpServer#main` 用 `java -cp target/test-classes` 拉起，进程退出与超时路径可断言 |
| MCP HTTP | `support/FakeHttpMcpServer` 挂在 `TestHttpServer` 上，只监听 `127.0.0.1` |

参考测试：端到端看 `WalkingSkeletonTest`（真实本地 HTTP 服务端）与 `FunctionCallingRunnerTest`（`@Mock` 回放），注解来源的等价性看 `AnnotationToolRegistrationTest`；回环语义看 `MaxRoundsTest`、`ToolFailureBackfillTest`、`IsolationTest`；方言看 `OpenAIDialectTest`、`AnthropicDialectTest`、`GeminiDialectTest`、`OpenAICompatibleClusterTest`；流式看 `*StreamAccumulatorTest`、`StreamAccumulatorDeterminismTest`、`ToolCallStreamListenerTest`、`StreamLoopRoundTest`；MCP 看 `Mcp*Test`、`StdioTransportTest`、`StreamableHttpTransportTest`。

## 9. 本版本的边界

- 工具在调用线程上**同步执行**，不提供超时/取消语义（长耗时任务请自行在 `ToolExecutor` 内提交到业务线程池）。
- 并行工具调用与 schema 严格模式三家均不支持；OpenAI 簇的 `parallel_tool_calls` 字段不写入报文。
- 不做对话历史的持久化、摘要与窗口裁剪（上下文长度治理另议）。
- 不接入 `lucky-context` 的 bean 后处理器做 `@Tool` 自动扫描，注册一律显式调用 `ToolRegistry#register(...)`；`@Tool` 方法只接收模型给出的参数，不做框架侧 SpEL 注入。
- 内核公共类（`HttpClientProxyObjectFactory`/`MethodContext`/`ExecuteMeta`）语义未改动，回环完全建立在既有插件机制之上。
