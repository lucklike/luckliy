## ⏫ 异步分片文件上传

HTTP中的异步分片文件上传通常是指将大文件分成多个小块（即“分片”），并通过多个请求异步上传这些小块。这样不仅可以加速上传过程，还能有效避免上传过程中因网络中断或其他问题导致整个文件上传失败。常见的实现方案一般包括以下几个步骤：

1. **将文件分片**

    - 大文件被分成多个较小的块（例如每个块 1MB 或 2MB），每个块都有自己的唯一标识（比如编号）。
    - 客户端需要读取文件并将其分成多个片段。

2. **上传每个分片**

    - 每个文件块单独进行异步上传，通常是通过 **multipart/form-data** 格式传输，也可以直接把分片的原始字节作为请求体传输。
    - 每个分片的上传请求通常会携带该分片的标识信息，比如`partNumber`和`totalParts`，以便服务器能够知道文件是由哪些部分组成的。

3. **服务器处理**

    - 服务器接收到分片文件时，可以保存分片并在后台进行合并，或者保存每个分片的临时状态。
    - 服务器需要根据每个请求中的标识信息，确定该分片属于哪个文件，并且能够按顺序将它们合并成完整的文件。

4. **合并文件**

    - 当所有分片都上传完成后，客户端或服务器可以发起一个请求来通知服务器合并这些分片为一个完整的文件。

5. **处理异常情况**

    - 如果某个分片上传失败，可以选择重新上传该分片。异步上传本身有助于在上传过程中遇到网络中断时进行恢复。
    - 服务器通常会在每个分片上传完成后向客户端发送状态反馈，客户端可以据此判断是否需要重试。

与分片下载不同，HTTP并没有为分片上传约定标准协议（下载有`Range`请求头），每个服务端的「查询已上传分片」「上传单个分片」「通知合并」，以及可选的「删除分片」几个接口的URL、参数名、响应结构都不一样。因此框架只约定**动作**，具体协议由你自己的API接口用注解声明出来，剩下的切分、并发、重试、断点续传、合并通知、合并失败后的分片清理由框架完成。

> 本文的每段客户端代码都有对应的可通过测试，可在
> [`ChunkUploadAnnotationTest`](../../../src/test/java/com/luckyframework/httpclient/generalapi/upload/ChunkUploadAnnotationTest.java)
> 及其`support`包下的假服务端中查到同款写法。

### # 使用`@ChunkUpload`注解来声明分片上传接口

这是推荐用法：一行注解搞定切分、并发上传、失败重传、断点续传与合并通知。

#### 1. 先实现服务端协议接口`ChunkUploadApi`

`ChunkUploadApi`规定了分片上传需要的几个动作，全部是default方法，实现时把方法接到真实接口上即可：

| 协议方法                                                | 说明                                                                                                                                       | 是否必须实现                                        |
|-----------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------|
| `boolean isChunkUploaded(String fileId, FileChunk fileChunk)` | 当前分片服务端是否已经收到，也是「分片用什么标识」的扩展点：片号协议在实现里查好已有片号集合后`contains(fileChunk.getIndex())`即可；服务端用片号之外的标识（分片ID、内容MD5等）时，覆写本方法、从`fileChunk`（索引/区间/大小/内容）取值比对即可，内核不关心标识长什么样。本方法每个分片调用一次，片数多时建议在覆写实现里缓存查询结果或转成Set再判断 | ❌ 默认返回`false`，即不跳过、每次全量上传                          |
| `boolean uploadChunk(String fileId, FileChunk fileChunk)` | 上传单个分片。入参给的是`FileChunk`对象，需要的字段从中拆；返回`false`或抛出异常都会被框架记录为“这片没传上去”并在下一轮重传                                                       | ✅（默认实现直接抛`ChunkUploadNotImplementedException`） |
| `boolean mergeChunks(String fileId, File file, int totalChunks)` | 通知服务端合并全部分片。只有在所有分片都上传成功之后才会被调用，文件名等信息由实现从`file`自行取用上报；服务端无需再判断分片是否齐全                                                                                       | ✅（同上） |
| `boolean deleteChunks(String fileId)` | 删除服务端已收到的该文件全部分片：可选的失败清理动作，只在开启`deleteOnMergeFailure`且合并请求**实际发起**仍失败后被调用；分片没传完而未发起合并时不会调用——那些分片留着下次续传还有用                                                                                       | ⚠️ 不启用删除开关无需覆写；启用则必须覆写（默认实现同`mergeChunks`抛`ChunkUploadNotImplementedException`，该异常只记入结果`getDeleteError()`与日志，不会向外抛） |

```java
@ServerAddress("http://localhost:8864/shard/upload/")
public interface FileChunkUploadApi extends ChunkUploadApi {

    /**
     * 判断分片是否已上传：先查服务端已有的片号集合，再与当前分片对账（断点续传）。
     * 服务端返回{"code":200,"data":[1,3]}，取data字段即为片号集合
     */
    @Override
    default boolean isChunkUploaded(String fileId, FileChunk fileChunk) {
        return uploadedChunks(fileId).contains(fileChunk.getIndex());
    }

    @Get("uploadChunks")
    @RespConvert("#{$body$.data}")
    List<Long> uploadedChunks(@Query("fileId") String fileId);

    /**
     * 协议接口要求入参是FileChunk，而表单协议要的是拆开的字段，用default方法拆解即可。
     * 接口代理会直接执行default方法体，方法体内的调用仍然会发出真实的HTTP请求
     */
    @Override
    default boolean uploadChunk(String fileId, FileChunk fileChunk) {
        return uploadChunkForm(fileId, fileChunk.getIndex(), fileChunk.getContent());
    }

    @Post("chunk")
    @RespConvert("#{$body$.data}")
    boolean uploadChunkForm(@MultiData("fileId") String fileId,
                            @MultiData("chunkNumber") long chunkNumber,
                            @MultiFile(value = "file", fileName = "chunk") byte[] content);

    /**
     * 通知服务端合并：收到的是原始文件，文件名从File取用后上报
     */
    @Override
    default boolean mergeChunks(String fileId, File file, int totalChunks) {
        return mergeRequest(fileId, file.getName(), totalChunks);
    }

    @Post("merge")
    @RespConvert("#{$body$.data}")
    boolean mergeRequest(@Query("fileId") String fileId,
                         @Query("fileName") String fileName,
                         @Query("totalChunks") int totalChunks);

    /**
     * 删除服务端分片：签名与协议方法一致时用注解直接覆写即可，
     * 只在开启deleteOnMergeFailure且合并失败后被调用；不启用该开关就不用写，
     * 启用则必须写（默认实现会抛ChunkUploadNotImplementedException）
     */
    @Override
    @Delete("chunks")
    @RespConvert("#{$body$.data}")
    boolean deleteChunks(@Query("fileId") String fileId);

    /**
     * 声明式分片上传：协议方法就在本接口上，所以无需再指定api属性
     */
    @ChunkUpload(chunkSize = "1048576", maxRetryCount = "5")
    ChunkUploadResult upload(File file);
}
```

几点实现约定：

- **协议方法可以照常使用本框架的一切注解**（`@Post`/`@MultiData`/`@MultiFile`/`@BinaryBody`/`@Retryable`等），它们各自发出真实的HTTP请求。
- **分片查询接口本身不是协议方法**，它只是`isChunkUploaded`实现里用到的普通注解方法：报文中存的是什么（片号、分片ID、`Map<片号,MD5>`、自定义DTO）完全由服务端决定，对账逻辑写在`isChunkUploaded(String, FileChunk)`里即可，内核只看它返回true/false。
- **上报哪些参数由服务端协议决定**：除了`fileChunk.getIndex()`与`fileChunk.getContent()`，`FileChunk`还提供`getStart()/getEnd()/getSize()`与`getTotalSize()/getChunkSize()/getTotalChunks()`，需要把区间或切分元数据一并上报时直接取用；分片内容也可以改用`fileChunk.writeContentTo(out)`流式写出，避免整片驻留内存。
- **不想用multipart表单**时，可以把分片字节作为二进制请求体上传，服务端直接读请求体（从`HttpServletRequest#getInputStream()`读，或用`@RequestBody byte[]`接收）：

  ```java
  @Override
  default boolean uploadChunk(String fileId, FileChunk fileChunk) {
      return uploadChunkBytes(fileId, fileChunk.getIndex(), fileChunk.getContent());
  }

  // URL模板里的#{param}会按参数名取值，等价于@Query("chunkNumber")
  @Post("chunk?fileId=#{fileId}&chunkNumber=#{chunkNumber}")
  @RespConvert("#{$body$.data}")
  boolean uploadChunkBytes(String fileId, long chunkNumber, @BinaryBody byte[] content);
  ```

- **`@MultiFile`标注`byte[]`/`InputStream`时必须给出`fileName`**：这类数据本身不带文件名，服务端无法把它识别为文件项；用`File`、`Resource`、`MultipartFile`、`HttpFile`或资源定位字符串（如`classpath:xx.txt`）时文件名已自带，`fileName`属性写了也无效。
- **返回`boolean`的方法要求服务端响应能被转成布尔值**，详见文末「常见坑」的第1条。

#### 2. `@ChunkUpload`支持的接口返回值类型

| 支持的返回值类型                | 说明                                     |
|--------------------------|----------------------------------------|
| `ChunkUploadResult`      | 完整的上传结果，含成功/跳过/失败的分片明细，**排查问题时最有用**     |
| `Boolean`/`boolean`      | 等价于`ChunkUploadResult#isSuccess()`     |
| `void`                   | 只关心流程是否跑完，不取结果；本方法仍然阻塞直到上传结束，需要异步时由调用方自己提交到线程池  |

#### 3. `@ChunkUpload`注解属性介绍

| 属性                    | 说明                                                                     | 默认值              | 是否支持`SpEL`表达式 |
|-----------------------|------------------------------------------------------------------------|------------------|---------------|
| `value`/`file`        | 待上传文件的位置，结果必须是`File`或文件路径字符串；留空时自动取方法参数列表中第一个`File`参数                       | `""`             | ✅             |
| `fileId`              | 文件唯一标识，用于查询已上传分片与通知合并；留空时使用文件内容的MD5                                 | `""`             | ✅             |
| `fileName`            | 服务端保存时使用的文件名；留空时使用原始文件名                                                 | `""`             | ✅             |
| `api`                 | 服务端协议接口的`Class`。留空（保持默认值`ChunkUploadApi`）时使用声明当前方法的接口，要求该接口继承`ChunkUploadApi`；协议方法与上传方法分开声明时在此指定 | `ChunkUploadApi` | ❌             |
| `chunkSize`           | 单个分片的字节数，声明为`String`：可写字面量`"1048576"`或表达式`#{chunkSize}`（结果须是数字），留空用默认5M | `""`             | ✅             |
| `maxConcurrency`      | 同时上传的分片数量上限，写法同上，留空用默认8                                    | `""`             | ✅             |
| `maxRetryCount`       | 分片失败后的最大重传**轮数**，写法同上，小于0表示无限重传直到全部上传成功；留空用默认3                       | `""`             | ✅             |
| `retryBackoffMillis`  | 每轮重传前的等待时间（毫秒），写法同上，留空用默认500                                              | `""`             | ✅             |
| `skipUploaded`        | 是否在上传前查询并跳过服务端已有的分片（断点续传）。服务端没有提供查询接口时应设为`false`                      | `true`           | ❌             |
| `mergeAfterSuccess`   | 是否在所有分片上传成功后自动通知服务端合并                                                   | `true`           | ❌             |
| `deleteOnMergeFailure` | 合并失败时是否删除服务端已上传的分片文件（调用`ChunkUploadApi#deleteChunks`）。只在合并请求**实际发起**且失败（返回`false`或抛异常）后触发；分片没传完而未发起合并时不会删除；删除失败不抛异常，只记录在结果里。开启前必须覆写`deleteChunks`（未覆写时默认实现抛`ChunkUploadNotImplementedException`，同样只记入结果），服务端没有删除接口时保持关闭 | `false`          | ❌             |

> **分片任务跑在哪个执行器上**：注解方式下分片统一提交给`MethodContext#getAsyncTaskExecutor()`返回的`AsyncTaskExecutor`（与`@RangeDownload`同一个路线），框架不会为分片上传自建线程池，同时在飞的分片数由`maxConcurrency`的提交窗口限定。需要换执行器时有两种方式：在当前方法上标注`@AsyncExecutor`（`executor`可写SpEL，`concurrency`进一步限制并发），或者直接给当前方法声明一个`AsyncTaskExecutor`类型的参数——**方法入参的优先级最高**，会覆盖注解与默认执行器。

需要把协议接口与普通业务接口分开声明时，用`api`属性指定：

```java
public interface FileUploadApi {

    @ChunkUpload(api = FileChunkUploadApi.class, chunkSize = "1048576")
    boolean upload(File file);
}
```

#### 4. 调用后必须判断结果

分片失败、重试用尽、合并失败都**不会抛异常**，而是把原因记录在返回值里，因此不能靠异常与否来判断成败：

```java
FileChunkUploadApi api = new HttpClientProxyObjectFactory().getProxyObject(FileChunkUploadApi.class);
ChunkUploadResult result = api.upload(new File("D:/big.zip"));
if (!result.isSuccess()) {
    log.warn("还有分片未上传成功：{}", result.getFailedChunks());
}
```

`ChunkUploadResult`的主要API：

| 方法                            | 说明                                                                                  |
|-------------------------------|-------------------------------------------------------------------------------------|
| `boolean isSuccess()`         | 整个流程是否成功：全部分片上传成功，且（不需要合并 或 合并已执行且成功）                                             |
| `boolean isAllChunksUploaded()` | 分片是否全部上传成功（与合并无关）                                                                    |
| `boolean isMerged()`          | 合并请求是否已执行且成功                                                                        |
| `Throwable getMergeError()`   | 合并请求抛出的异常；为`null`表示未发生异常。因分片未全部成功而**没有发起**合并时也返回`null`，此时原因看`getFailedChunks()`     |
| `boolean isDeleteRequired()`  | 合并失败后是否发起了分片删除（仅开启`deleteOnMergeFailure`且合并实际发起仍失败时为`true`）                          |
| `boolean isChunksDeleted()`   | 服务端已上传的分片是否删除成功；未删除、删除返回`false`或删除抛异常都返回`false`                                    |
| `Throwable getDeleteError()`  | 删除请求抛出的异常；未发起删除或因接口返回`false`而失败时返回`null`                                       |
| `List<ChunkResult<Boolean>> getSuccessChunks()` | 本次实际上传成功的分片结果，按索引升序，可从中取服务端返回的原始值                                                     |
| `List<Long> getAlreadyUploadedChunks()`     | 上传前服务端已存在、因而被跳过的分片索引                                                                 |
| `List<ChunkResult<Boolean>> getFailedChunks()` | 重试用尽后仍未上传成功的分片。`ChunkResult#getError()`非`null`表示上传时抛了异常，为`null`表示接口正常返回但返回了`false` |
| `int getRetryRounds()`        | 实际执行的重传轮数（不含首轮），可用于评估网络质量                                                            |
| `getFileId()`/`getFileName()`/`getTotalSize()`/`getChunkSize()`/`getTotalChunks()` | 本次上传的标识与切分元数据，空文件的`totalChunks`为0                                                   |

### # 使用`ChunkUploadExecutor`来编程式分片上传

需要自己控制上传时机（比如`fileId`来自主库的业务单号、合并要等业务状态就绪）时，直接用内核：

```java
public class ChunkUploadService {

    private final FileChunkUploadApi uploadApi;

    // 分片任务的执行池；编程式调用拿不到MethodContext，所以由本例自己创建
    private final ExecutorService uploadPool = Executors.newFixedThreadPool(8);

    public ChunkUploadService(FileChunkUploadApi uploadApi) {
        this.uploadApi = uploadApi;
    }

    public ChunkUploadResult upload(File file, String fileId) {

        ChunkUploadOptions options = new ChunkUploadOptions()
                .setChunkSize(1024 * 1024)      // 单片1M
                .setMaxConcurrency(4)           // 4个分片并发
                .setMaxRetryCount(-1)           // 无限重传直到全部成功
                .setRetryBackoffMillis(1000L)   // 每轮重传前等1秒
                .setSkipUploaded(true)          // 断点续传
                .setMergeAfterSuccess(false)    // 先不合并，由业务决定合并时机
                .setDeleteOnMergeFailure(true); // 合并失败时清理服务端分片（按需开启）

        // createByExecutor把一个普通的java Executor包装成AsyncTaskExecutor；
        // 内核只是使用它，既不会创建也不会关闭这个池，因此池的关闭仍由本例负责（见close方法）
        ChunkUploadResult result = new ChunkUploadExecutor(uploadApi, options,
                JavaThreadAsyncTaskExecutor.createByExecutor(uploadPool))
                .upload(file, fileId, file.getName());

        if (result.isAllChunksUploaded()) {
            // 自行决定何时合并，例如等业务单状态就绪后
            uploadApi.mergeChunks(fileId, file, result.getTotalChunks());
        }
        return result;
    }

    /**
     * 池由本例创建，所以也由本例关闭（内核不会帮你关）
     */
    public void close() {
        uploadPool.shutdown();
    }
}
```

- `upload(File, String)`两参重载会使用原始文件名。
- `ChunkUploadOptions`的属性与`@ChunkUpload`一一对应，含义也相同；非法配置（分片大小不大于0或超过`Integer.MAX_VALUE`、并发数不大于0、重传次数小于-1、等待时间为负）会在`upload`开始前的`validate()`中抛出`IllegalArgumentException`，不会传到一半才失败。
- **`AsyncTaskExecutor`是必填项**：`ChunkUploadExecutor(uploadApi, options, taskExecutor)`与省略配置的`ChunkUploadExecutor(uploadApi, taskExecutor)`都要求传入执行器，传`null`会在构造时抛`IllegalArgumentException`。内核**既不创建也不关闭任何线程池**，因此自建池的生命周期依旧归调用方。执行器类型来自`com.luckyframework.httpclient.proxy.async`包：编程式场景用`JavaThreadAsyncTaskExecutor.createByExecutor(executor)`包装现成的`Executor`，注解场景直接取`MethodContext#getAsyncTaskExecutor()`。
- `maxConcurrency`限制的是**同时在飞的分片任务数**（每提交满一批就等一批全部落定），与执行器自身的线程数无关：执行器线程数少于`maxConcurrency`时实际并发以线程数为准，多于时由提交窗口卡住，所以即便用的是框架共享池也不会被其他接口挤占。
- `upload`方法**阻塞**直到全部分片落定（含重试用尽），需要异步时请由调用方自己把本次调用提交到线程池。

### # 更底层：使用工具类`FileChunkHandle`来进行分片文件上传

`@ChunkUpload`与`ChunkUploadExecutor`把「查询→切分→并发上传→重传→合并」串成了一条固定流程。若服务端协议与这套流程差异较大（例如需要边上传边刷新进度条、或者要按业务规则决定重传策略），可以只用分片工具自己编排。

#### 1. 主要API介绍

| 重要的类                                                                                                              | 说明                                                                                                                                           | 主要方法                                                                                                                                                                                                                                                                                                                                                                                         |
|--------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| [FileChunk](../../../src/main/java/com/luckyframework/httpclient/generalapi/chunk/FileChunk.java)                  | `分片文件`，表示一个已经切分好的文件块，包含分片的`索引信息`、`区间[start,end)`、`切分元数据`等信息                                                                                        | `byte[] getContent()`：整片读入内存<br/>`void writeContentTo(OutputStream)`：分块写出，内存占用与分片大小无关<br/>`long getIndex()`：分片索引（从1开始）<br/>`long getStart()`/`getEnd()`/`getSize()`：区间与本片真实字节数<br/>`File getFile()`：原始文件<br/>`long getTotalSize()`/`getChunkSize()`/`int getTotalChunks()`：切分元数据，单片即可上报`fileSize/chunkSize/totalChunks` |

#### 2. 两种异步收集模式

|              | `asyncHandle`                                       | `asyncSettleHandle`                                                    |
|--------------|-----------------------------------------------------|------------------------------------------------------------------------|
| 分片抛异常       | 异常沿future向上传播，**不进入**结果集                            | 包装成`FAILED`状态的`ChunkResult`，**进入**结果集                                |
| 被止损跳过的分片   | **不进入**结果集                                          | 包装成`SKIPPED`状态的`ChunkResult`，**进入**结果集                                 |
| 返回的future   | 存在失败分片时以`CompletionException`异常完成                     | 除调度异常（如执行器拒绝任务）外**总是正常完成**                                              |
| `onComplete` | 必须有，且只能看到执行成功的分片                                      | 没有该参数——收尾逻辑直接写在future的链式回调里                                           |
| 适用场景        | 「失败就整体中止」，例如分片下载                                      | 「先全部提交、再根据结果重传」，即分片上传；`ChunkUploadExecutor`用的就是它的`AsyncTaskExecutor`版本                          |

需要注意：`classify`/`isAllSuccess(Function)`判断的是**业务返回值**，`getResults(ChunkResultStatus)`/`getUncompletedChunks()`判断的是**执行情况**，两个维度正交——一片可能执行成功但业务返回`false`，也可能执行失败而根本没有业务返回值。判据函数只会收到执行成功的分片的返回值，`FAILED`与`SKIPPED`的`null`不会传进去。

#### 3. 异步语义要点

1. **`asyncHandle`返回`CompletableFuture`，调用方必须消费它**（`join()`/`get()`/`exceptionally()`/`handle()`任选其一）：
   分片处理失败的原因只通过返回的future传播，不消费future就会把失败静默丢掉。
2. **`onComplete`无论成败都会被执行一次**，“清理临时文件”这类必须发生的收尾动作放在`onComplete`里是安全的；
   但不要把“通知服务器合并”也放在`onComplete`里：`onComplete`只能拿到【执行成功】的分片，
   抛异常失败与被跳过的分片对它不可见，仅靠`classify`会得到“全部成功”的错判，“合并”应放在future成功之后的链式回调里；
   同步`handle`则相反：任一分片抛异常就立即中断，`onComplete`不会执行。
3. **失败即止损**：某一分片失败后会置中断标志，尚未开始的分片直接跳过（已在运行的分片无法被打断），
   以减少无效请求；`asyncHandle`的结果集中只包含成功分片，`asyncSettleHandle`则三种状态齐全。
4. **异常层级固定为单层`CompletionException`**，`getCause()`即分片处理抛出的原始异常。
5. **`maxConcurrency`重载自建线程池**：线程数为`min(分片数, maxConcurrency)`、守护线程、命名`file-chunk-N`，
   全部分片任务落定后自动`shutdown`；传入`Executor`的重载则不会关闭调用方的执行器。
   传入`AsyncTaskExecutor`的重载同样不创建也不关闭执行器，并发完全由`maxConcurrency`的提交窗口控制，
   因此可以直接拿注解里的`context.getAsyncTaskExecutor()`来用（`ChunkUploadExecutor`与`@RangeDownload`都是这个做法）。
6. **空文件（长度为0）没有任何分片**：同步与异步路径都会正常执行`onComplete`，`maxConcurrency`重载也不会创建线程池。
7. **切分语义**：分片区间为`[start,end)`、索引从1开始、总大小恰为分片大小整数倍时不会产生末尾空分片；
   分片大小必须大于0且不超过`ChunkConstants.MAX_CHUNK_SIZE`（分片内容最终由`byte[]`承载）。

1. **用如下代码模拟服务器的分片上传接口**（这一版修掉了旧示例里的三处真实缺陷，见代码后的说明）

- 定义统一的响应结构

```java

@Data
public class Result<T> {

    private Integer code;
    private String message;
    private T data;

    public static <T> Result<T> success(T data) {
        Result<T> result = new Result<>();
        result.setCode(200);
        result.setMessage("Successful");
        result.setData(data);
        return result;
    }

    @SuppressWarnings("all")
    public static Result fail(Integer code, String message) {
        Result result = new Result();
        result.setCode(code);
        result.setMessage(message);
        return result;
    }

}
```

- 服务器代码，定义好以下关于分片文件上传的接口

> - `/shard/upload/uploadChunks` : 获取已经上传到服务器上的分片索引
> - `/shard/upload/chunk`：上传分片文件
> - `/shard/upload/merge`：合并分片文件

```java

@RestController
@RequestMapping("/shard/upload")
public class FileChunkUploadController {

    // 合并后文件的保存目录
    private static final String UPLOAD_DIR = "/Users/fukang/Desktop/test/shard/uploads/";
    // 用于存储分片文件的临时目录
    private static final String TEMP_DIR = "/Users/fukang/Desktop/test/shard/uploads/temp/"; // 临时存储分片的目录

    // 初始化目录
    public FileChunkUploadController() throws IOException {
        Files.createDirectories(Paths.get(UPLOAD_DIR));
        Files.createDirectories(Paths.get(TEMP_DIR));
    }

    /**
     * 获取已经上传的分片索引
     *
     * @param fileId 文件ID
     * @return 已经上传的分片索引（从1开始）
     */
    @GetMapping("uploadChunks")
    public Result<List<Integer>> uploadChunks(@RequestParam("fileId") String fileId) {
        File[] chunks = new File(TEMP_DIR + fileId).listFiles();
        if (chunks == null) {
            return Result.success(Collections.emptyList());
        }
        List<Integer> indexes = Stream.of(chunks)
                .map(f -> Integer.parseInt(f.getName()))
                .sorted()
                .collect(Collectors.toList());
        return Result.success(indexes);
    }

    /**
     * 上传分片文件
     */
    @PostMapping("/chunk")
    public Result<Boolean> uploadChunk(
            @RequestParam("fileId") String fileId,
            @RequestParam("chunkNumber") int chunkNumber,
            @RequestParam("file") MultipartFile file
    ) {
        try {
            // 保存分片
            String chunkDir = TEMP_DIR + fileId;
            Files.createDirectories(Paths.get(chunkDir)); // 创建分片目录

            File chunkFile = new File(chunkDir + "/" + chunkNumber);
            // 分片已存在时直接覆盖并返回成功：客户端的重试会让同一片重复到达，
            // 若此处返回失败（例如旧版的 Result.fail(100,"分片已存在")），客户端会把重复当成上传失败而无限重试下去
            Files.copy(file.getInputStream(), chunkFile.toPath(), StandardCopyOption.REPLACE_EXISTING);
            return Result.success(true);
        } catch (IOException e) {
            return Result.fail(500, "分片上传失败");
        }
    }

    /**
     * 合并分片文件
     */
    @PostMapping("/merge")
    public Result<Boolean> mergeChunks(
            @RequestParam("fileId") String fileId,
            @RequestParam("fileName") String fileName,
            @RequestParam("totalChunks") int totalChunks
    ) {
        try {
            String chunkDir = TEMP_DIR + fileId;

            // 客户端保证只有全部分片上传成功后才会调用本接口，这里再校验一次即可快速暴露异常请求
            for (int i = 1; i <= totalChunks; i++) {
                if (!new File(chunkDir + "/" + i).exists()) {
                    return Result.fail(100, "缺少分片文件：" + i);
                }
            }

            // 合并文件：必须用覆盖写，若用new FileOutputStream(outputFile, true)的追加模式，
            // 同一个文件合并两次就会得到内容叠加的坏文件
            File outputFile = new File(UPLOAD_DIR + fileName);
            try (OutputStream out = new BufferedOutputStream(new FileOutputStream(outputFile))) {
                for (int i = 1; i <= totalChunks; i++) {
                    Files.copy(new File(chunkDir + "/" + i).toPath(), out);
                }
            }

            // 删除分片目录
            for (int i = 1; i <= totalChunks; i++) {
                new File(chunkDir + "/" + i).delete();
            }
            new File(chunkDir).delete();

            return Result.success(true);
        } catch (IOException e) {
            return Result.fail(500, "文件合并失败");
        }
    }
}
```

- 关于这一版的三处修正：

  1. **分片重复到达必须返回成功**（旧版返回`Result.fail(100, "分片已存在")`）。客户端在网络抖动时会重传同一片，服务端把「已存在」判为失败会破坏接口的幂等性，让重传永远成功不了。
  2. **合并必须用覆盖写**（旧版是`new FileOutputStream(outputFile, true)`的追加模式）。追加模式下同一个文件合并两次，内容会直接翻倍叠加成一个坏文件。
  3. **合并前按`totalChunks`校验分片是否齐全**（旧版只判断目录非空，缺片时会静默产出截断文件）。为此合并接口需要多收一个`totalChunks`参数，客户端的`mergeChunks`协议方法也正好提供了它。

  另外旧版的查询接口返回`Map<片号, 分片MD5>`，客户端还得逐片算MD5来比对；如果服务端保存的分片内容就是客户端发出的原始字节，直接返回**已有片号列表**更简单，断点续传的效果也完全一样——所以本文的示例采用`List<Integer>`。若确实需要校验分片内容是否损坏，既可以让服务端只返回「校验通过的片号」，也可以返回`Map<片号,MD5>`这类复合报文并覆写`isChunkUploaded`逐片比对，两种形态内核都支持。

2. **用`FileChunkHandle`来封装分片上传逻辑**

```java

@ServerAddress("http://localhost:8864/shard/upload/")
public interface ManualChunkUploadApi {

    //-----------下面三个协议方法的写法与注解那一节一致，只是不必继承 ChunkUploadApi------------//

    @Get("uploadChunks")
    @RespConvert("#{$body$.data}")
    List<Long> uploadedChunks(@Query("fileId") String fileId);

    @Post("chunk")
    @RespConvert("#{$body$.data}")
    Boolean uploadChunk(@MultiData("fileId") String fileId,
                        @MultiData("chunkNumber") long chunkNumber,
                        @MultiFile(value = "file", fileName = "chunk") byte[] content);

    @Post("merge")
    @RespConvert("#{$body$.data}")
    Boolean mergeChunks(@Query("fileId") String fileId,
                        @Query("fileName") String fileName,
                        @Query("totalChunks") int totalChunks);

    /**
     * 分片文件上传方法
     *
     * @param file      待上传的文件
     * @param chunkSize 分片大小
     * @throws Exception 计算文件MD5时抛出的IO异常
     */
    default void uploadFile(File file, long chunkSize) throws Exception {
        // 获取分片处理器
        FileChunkHandle chunkHandle = FileChunkHandle.of(file, chunkSize);
        // 构造用于执行异步上传任务的线程池（由本例自己创建，也需要本例关闭；
        // 不想自管线程池时可改用asyncSettleHandle(onHandle, 8)重载，
        // 线程池由处理器内部创建（守护线程、命名file-chunk-N）并在任务落定后自动关闭；
        // 手上已有AsyncTaskExecutor时（例如注解方法里的context.getAsyncTaskExecutor()），
        // 改用asyncSettleHandle(taskExecutor, onHandle, 8)重载，既不建池也不关池）
        ExecutorService executor = Executors.newFixedThreadPool(10);

        // 生成文件唯一的ID（这里用内容MD5，同一份文件重复上传时可以从断点处继续）
        String fileId = DigestFunctions.md5Hex(file, "UTF-8");
        // 获取文件名
        String fileName = file.getName();
        // 调用服务器接口获取所有已经上传的分片报文（手动编排时按本页协议自定类型）
        Set<Long> uploadedSet = new HashSet<>(uploadedChunks(fileId));

        chunkHandle.asyncSettleHandle(executor, fileChunk -> {
                    // 已经上传了的情况：直接返回成功，不再发请求
                    if (uploadedSet.contains(fileChunk.getIndex())) {
                        return true;
                    }
                    // 没有上传的情况；这里把返回值原样交出去，服务端返回false也算一片失败
                    else {
                        return uploadChunk(fileId, fileChunk.getIndex(), fileChunk.getContent());
                    }
                })
                .thenAccept(rs -> {
                    // settle模式下future总是正常完成，成功、异常失败、被跳过的分片全都在rs里
                    if (rs.hasExecutionFailure()) {
                        // 有分片连请求都没发出去（被止损跳过）或者上传时抛了异常
                        rs.getUncompletedChunks().forEach(chunk -> {
                            // 记录待重试的片号，chunk可以定位区间后原样重传
                        });
                        return;
                    }
                    // 剩下的都是执行成功的分片，再按业务返回值分类
                    ChunkResultClassify<Boolean> classify = rs.classify(r -> Boolean.TRUE.equals(r));
                    if (!classify.isAllSuccess()) {
                        classify.failureForEach(r -> {
                            FileChunk fileChunk = r.getFileChunk();
                            // 处理返回失败的结果，例如记录待重试的片号
                        });
                        return;
                    }
                    // 走到这里说明所有分片都上传成功了，通知服务器合并
                    mergeChunks(fileId, fileName, rs.size());
                })
                .exceptionally(cause -> {
                    // 只有调度异常（如线程池拒绝任务）才会走到这里，cause为单层CompletionException
                    System.err.println("分片上传失败：" + cause.getCause().getMessage());
                    return null;
                })
                .whenComplete((unused, throwable) -> executor.shutdown());
    }

}
```

- 如果希望拿到服务端返回的完整报文（比如要把`message`写进日志），协议方法的返回值也可以直接声明成包装类型，
  例如`Result<Boolean> uploadChunk(...)`（此时**不要**再加`@RespConvert`，框架会把整个JSON反序列化成该对象），
  分类判据相应写成`r -> r.getCode() == 200`。
- 不想让方法抛出`Exception`时，`DigestFunctions.md5Hex`那一步可以用`try/catch`包住，或者用lombok的`@SneakyThrows`。

- 只重传失败子集时，用静态重载`FileChunkHandle.asyncSettleHandle(List<FileChunk>, Executor, Function)`（或者不自己管线程池的
  `asyncSettleHandle(List<FileChunk>, AsyncTaskExecutor, Function, int maxConcurrency)`版本），
  把上一轮`getUncompletedChunks()`拿到的分片原样提交即可，不必为了重传几片而重新切分整个文件：

```java
// previousResults是上一轮asyncSettleHandle的结果集
List<FileChunk> pendingChunks = previousResults.getUncompletedChunks();
ChunkResults<Boolean> results = FileChunkHandle
        .asyncSettleHandle(pendingChunks, executor, chunk -> uploadChunk(fileId, chunk.getIndex(), chunk.getContent()))
        .join();
```

### # 常见坑

1. **返回`boolean`的接口，服务端不能返回`text/plain`**

   框架解析响应体时，只有`application/json`、`application/xml`等结构化媒体类型才会做反序列化与类型转换；`text/plain`会原样作为字符串返回，此时代理方法在把返回值转成声明的`boolean`时会抛出`String cannot be cast to Boolean`一类的异常。所以：

    - 服务端返回`{"code":200,"data":true}`（`application/json`），客户端用`@RespConvert("#{$body$.data}")`取出`data`，这是本文示例采用的写法；
    - 或者服务端直接返回`true`且媒体类型是`application/json`；
    - 如果服务端只能返回纯文本，请把协议方法的返回值声明为`String`，自己判断内容。

2. **`fileId`留空会完整读一遍文件算MD5**

   几十GB的大文件这次读取并不便宜，需要业务标识（如订单号+文件名）时用`fileId`属性直接给出，别依赖兜底的MD5。

3. **失败不抛异常，必须判断返回值**

   `@ChunkUpload`与`ChunkUploadExecutor`都遵循「把失败写进结果」的约定：分片重试用尽、合并接口返回失败、合并接口抛异常，都只是让`isSuccess()`变成`false`。想要「失败即抛出」时自己判断结果再抛，或者用`boolean`返回值配合告警。

4. **服务端没有查询接口时要关掉`skipUploaded`**

   `isChunkUploaded`保持默认实现（返回`false`）时，开与不开都只表现为「每次全量上传」，不报错；但显式关掉能省掉逐分片一次的无用方法调用（若查询接口是注解方法，就是省掉片数次HTTP请求）。

5. **`deleteOnMergeFailure`只对「合并实际失败」生效，且开启前必须覆写`deleteChunks`**

   分片没传完而未发起合并时不会删除服务端分片——那些分片下次续传还要用；如果希望合并重试前清理旧分片，请自行调用`ChunkUploadApi#deleteChunks`。另外`deleteChunks`与`mergeChunks`一样没有可兜底的默认协议：服务端没有删除接口时不要开启本属性，否则每次合并失败都会被默认实现的`ChunkUploadNotImplementedException`撞上——异常只记入`getDeleteError()`不影响主流程，但删除不会真正发出请求，孤儿分片依旧留在服务端。

6. **空文件不会有分片**

   长度为0的文件切分结果为空集合，此时`totalChunks=0`，仍会按`mergeAfterSuccess`的约定通知服务端合并，由服务端决定如何创建空文件。

7. **断点续传依赖服务端保存的分片内容可信**

   跳过已上报的片号意味着信任服务端那一片是完整的。若担心分片内容在上一轮被写坏，请让服务端只返回校验通过的片号，或者关掉`skipUploaded`全量重传。
